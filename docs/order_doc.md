# SnowVillage デモアプリ開発指示書
## 異なる書式のPDF発注書をSnowflakeで受注データ化する

**開発担当：Snowflake CoCo（Cortex Code）**

### 1. プロジェクトの目的

Snowflakeの機能を使用して、企業間の商品受発注業務におけるPDF発注書の取り込み、AIによる情報抽出、データの標準化、業務ルールによる検証、受注データの確定、処理履歴管理までを実演できるデモアプリケーションを開発してください。

ユーザーインターフェースはStreamlit in Snowflakeで構築します。

今回のデモで特に伝えたいのは次の3点です。

1. 取引先ごとに発注書のレイアウトが異なっていても、共通のデータ形式に変換できる。
2. AIによる情報抽出だけでなく、商品マスタとの照合や金額検算など、業務上必要な検証まで実行できる。
3. 受け取った発注書がどのように処理されたか、成功・失敗・修正内容を後から確認できる。

**画面だけのモックアップではなく、Snowflake上で実際に動作するEnd-to-Endのデモ環境を完成させてください。**

### 2. 想定する業務シナリオ

架空の事務用品卸売企業が、複数の取引先企業から商品発注書を受け取る業務を想定します。

- 発注側：複数の企業。それぞれ独自書式のPDF発注書を使用。
- 受注側：事務用品卸売企業。今回のアプリケーションを利用。
- 業務担当者：受け取ったPDF発注書をStreamlitの画面でアップロード。
- システム：注文情報を抽出し、受注データに標準化して検証。
- 業務担当者：必要な修正を行い、受注確定。

外部の販売管理システムとの連携までは実装しません。確定した受注データをSnowflakeのテーブルに保持するところを今回のゴールとします。

### 3. デモの操作フロー

以下のフローをStreamlitの画面から操作できるようにしてください。

1. PDF発注書を選択またはドラッグ＆ドロップする。
2. 「アップロード」ボタンを押す。
3. PDFがSnowflakeの内部ステージに保存され、受付記録が作成される。
4. 「AIで読み取り」ボタンを押す。
5. Cortex AIがPDFから発注情報を抽出する。
6. 抽出した情報を共通フォーマットに変換する。
7. マスタ照合、必須項目、金額計算などの検証を実行する。
8. 画面に抽出された受注データと検証結果を表示する。
9. 問題がある場合は画面上で修正し、再検証できる。
10. 検証に合格したら「受注確定」する。
11. 受注一覧と処理履歴に結果を反映する。

画面をリロードしたり、別のセッションで開き直した場合も、保存済みデータと処理状況を復元できる構造にしてください。

### 4. 技術構成

基本的にSnowflakeのネイティブ機能だけで構成してください。

| レイヤー | 使用する技術 |
|---|---|
| UI | Streamlit in Snowflake |
| PDFアップロード | Streamlit file_uploader + Snowpark Python |
| ファイル保管 | Snowflake Internal Stage |
| AI情報抽出 | Cortex AI_EXTRACT |
| 補助的な文書解析 | AI_PARSE_DOCUMENT（必要時のみ） |
| 標準化 | Snowflake SQL / Snowpark Python |
| データ検証 | SQL / Python |
| 業務データ管理 | Snowflake Tables |
| 操作・処理履歴 | Snowflake Tables |
| 開発・デプロイ | Snowflake CoCo / Snowflake CLI |

PDFの構造化には、PDFを直接入力可能な `AI_EXTRACT` を第一候補とします。

特別な事情がなければ、外部OCRサービス、外部API、外部データベースは使用しないでください。

### 5. Snowflakeリソースの命名規則

デモで作成するリソースを他の環境から明確に識別し、後から安全に削除できるように、作成するすべてのリソース名に `SNOWVILLAGE_` 接頭辞を付けてください。

少なくとも以下を用意してください。

| 種別 | 名称 |
|---|---|
| データベース | SNOWVILLAGE_DB |
| ロール（開発・所有者） | SNOWVILLAGE_APP_OWNER_ROLE |
| ロール（閲覧・利用者） | SNOWVILLAGE_VIEWER_ROLE |
| ウェアハウス | SNOWVILLAGE_WH |
| スキーマ | SNOWVILLAGE_RAW |
| スキーマ | SNOWVILLAGE_CORE |
| スキーマ | SNOWVILLAGE_APP |
| PDF保存ステージ | SNOWVILLAGE_PDF_STAGE |
| アプリコード保存ステージ | SNOWVILLAGE_APP_STAGE |
| Streamlitアプリ | SNOWVILLAGE_ORDER_INTAKE_APP |

必要に応じて他のリソースを追加して構いませんが、同じ命名規則に従ってください。

ウェアハウスは原則としてX-SMALL、AUTO_SUSPENDを有効にして、デモ費用を抑えてください。

既存オブジェクトが存在する場合は定義を確認し、無条件で `CREATE OR REPLACE` しないでください。

既存のSnowflake環境にある他用途のオブジェクトは変更・削除しないでください。

### 6. PDFファイルのアップロード

Streamlitで `st.file_uploader` を使用し、ユーザーがブラウザからPDFをアップロードできるようにしてください。

要件：

- ドラッグ＆ドロップに対応。
- 単一PDFに加え、複数PDFの一括アップロードにも対応。
- PDF以外は受け付けない。
- ファイルの拡張子だけでなく、PDFの実体も検証。
- デモ用途として1ファイル20MB程度を上限とする。
- アップロード処理の成功・失敗を画面に表示する。
- ファイルをSnowflake内部ステージに保持する。

ステージへのアップロードには、Snowpark Pythonの `session.file.put_stream()` を優先的に利用してください。

PDFはバイナリのまま保存し、`auto_compress=False` を指定して、後続のAI処理で参照できることを確認してください。

アップロード時にUUIDで受付IDを発行し、受付IDに基づくステージパスへ保存してください。元のファイル名だけを一意キーとして使用しないでください。

ファイルのSHA-256ハッシュも計算・保存します。

同一内容のファイルを再アップロードした場合は重複と判定し、既存の受付履歴へ誘導してください。新たな受注を自動作成しないでください。

なお、アップロード成功はステージへの保存成功を確認してから記録してください。

### 7. Cortex AIによる発注書の情報抽出

Snowflakeの `AI_EXTRACT` を使用します。

PDFを `TO_FILE()` で参照し、次の項目を構造化して抽出してください。

**発注ヘッダー情報**

| 項目名 | 内容 |
|---|---|
| order_number | 発注番号 |
| order_date | 発注日 |
| buyer_name | 発注元会社名 |
| supplier_name | 発注先会社名 |
| delivery_date | 希望納品日 |
| delivery_address | 納品先 |
| subtotal | 税抜合計 |
| tax_amount | 消費税額 |
| total_amount | 税込合計 |
| notes | 備考 |

**発注明細情報**

| 項目名 | 内容 |
|---|---|
| line_number | 明細番号 |
| product_code | 発注側商品コード |
| product_name | 商品名 |
| specification | 商品規格 |
| quantity | 発注数量 |
| unit | 数量単位 |
| unit_price | 単価 |
| line_amount | 明細金額 |

実装上の注意：

- AI_EXTRACTの公式ドキュメントでサポートされているJSON Schema形式を使用する。
- 明細は公式仕様に従い、列ごとの文字列配列として抽出し、アプリケーション側で行形式に変換する。
- 配列の長さが一致しない場合、黙って欠損値を補完せず、検証エラーとして扱う。
- PDFに存在しない項目をAIに推測させない。
- 値が存在しない場合はNULLとして扱えるようにする。
- 発注側の表記をそのまま保持するRAWデータと、標準化したデータを区別する。
- 抽出元のJSONレスポンスは加工せず履歴として保存する。
- `scores => TRUE` を利用し、抽出スコアを取得できるようにする。

AI_EXTRACTのスコアは、あくまでも抽出品質の参考値として扱ってください。特に明細テーブルのスコアはテーブル全体の評価であり、各セルの正しさを保証するものではありません。

単独のスコアだけで受注データが正しいと判定しないでください。

また、抽出エラーの際は原因を履歴に記録し、失敗した処理を再実行できるようにしてください。

### 8. データの標準化

取引先による違いを吸収して、受注データを共通の構造に変換してください。

想定する差異：

- 「発注番号」「注文No.」「PO番号」などの項目名の違い。
- 発注書内の項目配置の違い。
- 「株式会社」の有無など会社名表記の違い。
- 商品名や商品コードの違い。
- 日付の表記形式の違い。
- カンマや円記号を含む数値。
- 税抜・税込表記の違い。
- 複数ページにまたがる明細。

日付はDATE型、金額はNUMBER型など、適切な型へ変換してください。

数量・金額の標準化では、元の値と変換後の値を対応付けられるようにしてください。

発注書上の情報と商品マスタ上の情報が矛盾した場合、勝手に商品マスタの値で置き換えないでください。

契約単価や取引先固有の商品コードが存在する可能性を考慮して設計してください。

### 9. デモ用マスタデータ

次の3種類のマスタを作成してください。

**CUSTOMERS：取引先マスタ**

- 取引先ID
- 取引先正式名称
- 名称別名
- 有効・無効

**PRODUCTS：商品マスタ**

- 自社商品コード
- 自社商品名
- 標準単位
- 参考単価
- 税区分
- 有効・無効

**CUSTOMER_PRODUCT_MAP：取引先商品コード対応マスタ**

- 取引先ID
- 発注側商品コード
- 自社商品コード
- 発注側商品名
- 単位換算係数（必要なら）

デモ向けに、実在しない架空の取引先を3社以上用意してください。

商品はコピー用紙、トナーカートリッジ、クリアファイルなど、一般的な事務用品を5種類程度登録してください。

商品マッピングについては、発注側の商品コードが会社によって異なるケースを必ず含めてください。

### 10. 業務データのテーブル設計

少なくとも次のテーブルを作成してください。テーブル名にも `SNOWVILLAGE_` 接頭辞を付けてください。

**RAW層**

- DOCUMENTS：ファイル受付、保存先、ハッシュ、受付者、受付日時、状態。
- EXTRACTION_RUNS：AI抽出の実行履歴、抽出結果JSON、スコア、エラー、処理時間、実行日時。

**CORE層**

- CUSTOMERS：取引先マスタ。
- PRODUCTS：商品マスタ。
- CUSTOMER_PRODUCT_MAP：取引先商品対応マスタ。
- ORDER_HEADERS：標準化された受注ヘッダー。
- ORDER_LINES：標準化された受注明細。
- VALIDATION_RESULTS：検証ルールごとの実行結果。
- AUDIT_LOG：画面からの操作、修正、確定、再処理などの履歴。

受付IDと受注IDは区別してください。

同一のPDFに対して複数回のAI抽出を行った場合も、それぞれの実行履歴を保持してください。

受注データを修正する場合は、修正前後の値と修正者、修正日時が分かるようにしてください。

処理中の部分的なデータが、確定した受注データとして参照されない設計にしてください。

### 11. データ検証

抽出したデータに対して次の検証を実装してください。

| 検証項目 | 判定内容 |
|---|---|
| 必須項目 | 発注番号、発注日、取引先が存在するか |
| 取引先照合 | 発注元会社がマスタに存在するか |
| 商品照合 | 発注側商品コードが自社商品へ対応付けられるか |
| 数量検証 | 数量が正の数であるか |
| 明細検証 | 明細が1行以上あり、列の整合性が取れているか |
| 金額検算 | 数量×単価が記載金額と整合するか |
| 合計検算 | 明細合計、税額、総合計が整合するか |
| 日付検証 | 日付として解釈可能か |
| 重複検証 | ファイル重複や発注番号の重複がないか |

検証結果は次の3段階に分類してください。

- PASS：問題なし
- WARNING：確認を推奨するが、業務上は確定可能
- ERROR：解消するまで受注確定を禁止

金額の丸め、消費税、単位換算などは、実装した計算ルールをREADMEに明記してください。

発注書に単価や税額が存在しない場合は、存在しない情報を理由に必ずERRORとするのではなく、業務上適切なWARNINGまたは確認待ちとして扱う設計を検討してください。

税率は固定値をコードに埋め込まず、商品やマスタから判定可能にしてください。

**AI抽出が完了したことだけをもって、検証成功としてはなりません。**

### 12. 処理状況と履歴管理

ファイルごとの処理状況を管理してください。

| 状態 | 意味 |
|---|---|
| UPLOADED | PDF受付・保存完了 |
| EXTRACTING | AI抽出中 |
| NEEDS_REVIEW | 抽出・検証後、確認または修正待ち |
| READY | 検証が通り確定可能 |
| CONFIRMED | 受注確定済み |
| FAILED | 技術的な処理失敗 |
| DUPLICATE | 重複ファイルとして受付 |

各状態の遷移日時を記録してください。

エラーによって処理が中断した場合も、受付記録が消えてはいけません。

確定済み受注を再処理する場合、既存の確定データを無断で上書きせず、再処理履歴と変更内容を保持してください。

また、処理状況はStreamlitのセッションだけで管理せず、Snowflakeの永続テーブルへ保存してください。

### 13. Streamlit画面の設計

UIは日本語で作成してください。

業務担当者が直感的に操作でき、なおかつ登壇デモで一連の仕組みを理解してもらいやすいデザインを目指してください。

最低限、次の4つの機能を実装してください。

**画面A：発注書アップロード**

- PDFファイルの選択・ドラッグ＆ドロップ。
- ファイル名、ファイルサイズの表示。
- アップロード実行ボタン。
- 成功・失敗メッセージ。
- PDFの受付ID表示。

**画面B：AI抽出・受注確認**

- 処理対象PDFの選択。
- AI抽出実行ボタン。
- 抽出中の状態表示。
- PDF原本の参照またはダウンロード。
- 抽出されたヘッダー情報の表示。
- 明細行を表形式で表示。
- 発注側商品コードと、自社商品コードの対応表示。
- 抽出された値の編集。
- 再検証ボタン。
- 検証結果一覧。
- 受注確定ボタン。

可能であれば、PDFの内容と抽出結果を左右に並べて表示してください。

ただし、PDFプレビューが使用ランタイムの制限で実現できない場合は、原本のダウンロード機能を必須の代替手段としてください。

**画面C：受注一覧**

- 受付日、取引先、発注番号、ステータスの一覧。
- ステータス・取引先による絞り込み。
- 受注ヘッダーと受注明細の確認。
- 確定済み受注のCSVダウンロード。
- 受付IDから原本と処理履歴を参照。

**画面D：処理状況・監査**

上部に以下のKPIをカード形式で表示してください。

- 受付済みPDF件数
- 処理成功件数
- 確認待ち件数
- 処理失敗件数
- 確定済み受注件数

下部にファイルごとの処理履歴を表示してください。

どのPDFがいつ受付され、抽出され、検証され、確定されたかを追跡できるようにします。

画面内のユーザー識別には、Snowflake公式に対応する `st.user` の利用を優先してください。

### 14. 受付データの完全性確認

この機能は今回の重要な要件です。

PDFからデータを抽出するだけでなく、アップロードされたPDFが漏れなく処理されたかを確認できるようにしてください。

以下の整合性を管理してください。

- アップロードを受け付けたファイル数
- ステージへの保存に成功したファイル数
- AI抽出を実行したファイル数
- AI抽出に成功したファイル数
- 検証に合格したファイル数
- 受注確定したファイル数
- 未処理・失敗・確認待ちのファイル数

受付記録を起点として、処理結果が存在しないPDFを検出できることが必要です。

ステージ上のファイル存在確認方法については、使用するStreamlitランタイムの権限・制限を確認して実装してください。

例えば、ステージ保存に失敗しているのに受付成功と表示される、AI抽出に失敗しているのに処理済みになる、という状態を防いでください。

ただし、アプリへアップロードされていない外部の発注書まで検出できるわけではありません。今回の完全性管理の対象は、アプリで受付を試みたPDFとします。

### 15. デモ用PDF発注書の作成

デモに使用するPDFファイルも作成してください。

架空の企業3社から発行された発注書を想定し、それぞれ異なるレイアウトにしてください。

**サンプルA：一般的な発注書**

- A4縦
- 発注番号・発注日・発注元が上部に記載
- 明細が表形式
- 単価・数量・金額が記載
- 税抜合計、消費税、税込合計が明確
- AI抽出・検証が正常終了するケース

**サンプルB：書式が大きく異なる発注書**

- A4横、または上下に配置が異なるレイアウト
- 「注文No.」「品番」「希望納期」など別の項目名
- 取引先独自の商品コード
- サンプルAとは異なる日付形式
- 同じ商品を異なるコード・名称で指定
- 商品コードの変換を含め、正常に標準化できるケース

**サンプルC：例外がある発注書**

- スキャン画像を含むPDF、または画像化されたPDF
- 読み取りが比較的難しいレイアウト
- 商品マスタに存在しない商品を1つ含む
- 明細金額または合計金額に意図的な不整合を含む
- 検証エラーによって受注確定がブロックされるケース

サンプルAの再アップロードによる重複検出もデモ可能にしてください。

PDFには会社情報、発注番号、担当者、納品先、明細、金額などを含め、実務で使われる発注書に近い体裁にしてください。

ただし、すべて架空の情報を使用し、実在する企業の正式な発注書と誤認されないようにしてください。

PDF生成に使った元データをJSONまたはCSVで保持し、期待値として抽出結果の自動テストに利用してください。

### 16. テストと受入条件

以下のテストを作成・実行してください。

- [ ] サンプルAをアップロードし、PDFがステージへ正常保存される。
- [ ] サンプルAの発注番号・取引先・商品明細が正しく抽出される。
- [ ] サンプルBでレイアウトの違いを吸収できる。
- [ ] サンプルBの取引先商品コードが自社商品コードへ変換される。
- [ ] サンプルCで検証ERRORが表示され、受注確定が禁止される。
- [ ] サンプルCの不備を画面で修正し、再検証・確定できる。
- [ ] サンプルAを再アップロードすると重複検出される。
- [ ] 同じ発注番号で内容の異なるPDFが届いた場合、無断で上書きされない。
- [ ] AI抽出失敗時にFAILEDとなり、再処理が可能。
- [ ] 受注確定後、一覧に反映される。
- [ ] 画面を再読み込みしても受付・処理履歴が残る。
- [ ] 原本PDFと抽出結果・検証結果を受付IDから追跡できる。
- [ ] 画面の操作に応じてSnowflakeの実テーブルが更新される。

正常系だけでなく、異常系や再処理も含めて動作確認してください。

AIの抽出結果には揺らぎがあるため、実行ごとに変わり得る抽出精度と、決定論的な検証ロジックのテストは分けてください。

### 17. セキュリティ・権限・費用

- Snowflake認証とRBACを利用する。
- ロールの権限を必要最小限とする。
- アプリの利用ロールと開発・管理ロールを分離する。
- 実データや認証情報をソースコードへ埋め込まない。
- SQL実行時は安全なパラメータ化を行う。
- PDFから得られた文章をシステムへの命令として扱わない。
- Cortex AIの利用可能リージョンを確認する。
- クロスリージョン推論が必要な場合は、設定変更の前に利用者の承認を求める。
- 可能な範囲でAIの処理時間やコストを把握できるようにする。

Streamlitの実行には、まず明示的にウェアハウスランタイム `SYSTEM$WAREHOUSE_RUNTIME` を指定する構成を検討してください。

ファイルアップロード、PDF処理、必要なPythonライブラリ、Snowflake権限が成立することを事前検証します。

機能制約によってコンテナランタイムが必要になる場合は、Compute Poolの追加費用と権限を説明したうえで変更してください。

### 21. 優先順位

今回は15分程度の技術イベントで使用するデモです。

そのため、複雑な本番運用機能よりも、次の体験を確実に見せられることを優先してください。

**最優先（必須）**

- StreamlitからPDFをアップロードできる。
- 異なる書式のPDFから発注データを抽出できる。
- 抽出データが共通の受注データに変換される。
- 検証成功と検証失敗を画面で確認できる。
- 検証結果が履歴として残る。
- 受注を確定し、受注一覧で参照できる。

**次に優先**

- 複数PDFの一括処理。
- 重複検出。
- PDF原本との並列表示。
- CSV出力。

**余裕があれば**

- 処理時間・AI使用コストの表示。
- AI抽出スコアの表示強化。
- 複数ページ明細の高度な処理。
